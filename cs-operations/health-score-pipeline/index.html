From a spreadsheet to a Monday-morning alert

A health score only helps if someone sees it change in time. I moved my 80-account health score out of Excel and into SQL, so it can run every week on a fresh CRM export, remember last week's scores, and tell the team in Slack what changed.

Skill shown
CS operations: turning a manual model into a repeatable, integrated process
The problem
The Excel model works, but someone has to export the data, paste it in and read the results. It goes stale between refreshes, it has no memory of last week, and nobody is told when an account slips.
What I did
Rebuilt every rule of the score as SQL views, added a score history and week-on-week alerts, and wrapped it in a small script that loads the CRM export and posts a summary to Slack through an incoming webhook.
Result
The same results as the Excel model for all 80 accounts: the same scores, bands, priority order and expansion candidates, and the same £370,750 ARR at risk. The weekly refresh is now one command that can run on a schedule.
Tools used
SQL (SQLite), Slack incoming webhooks, Python glue script (written with Claude), Excel for the original model

All accounts and figures are fictional, from the Customer Health Score Model. The score rules are unchanged; only where they run has changed.

Why move it out of Excel

Excel is the right place to design a score: anyone can see the weights and change a threshold. It's the wrong place to run one every week. Three things were missing:

  • Freshness. The score is only as current as the last time someone pasted in an export.
  • Memory. The sheet shows this week. It can't say that an account was green last week and is amber now, and that change is the most useful signal a CSM can get.
  • Reach. Results sit in a file. The team works in Slack and the CRM.

How it works

  1. Load. The CRM export (CSV) goes into a SQLite table, with each column typed so numbers compare as numbers.
  2. Score. A SQL view, scored_accounts, applies the same rules as the Excel Inputs sheet: signal thresholds, dimension weights, hard caps, bands, priority and plays.
  3. Remember. Each run saves every account's score to a score_history table. Rerunning the same day replaces that day's scores, so a mistake is easy to redo.
  4. Compare. A second view, score_changes, compares this run with the last one and raises an alert for each account that needs attention.
  5. Tell the team. The script builds a short summary and posts it to a Slack channel. Without --post it only prints it, so it's safe to test.

The score in SQL

Each signal is a CASE expression against the thresholds from the Excel model. This is the escalation signal, and the hard cap that stops a happy-looking account with an unpaid invoice from showing as healthy:

CASE WHEN escalated_tickets = 0 THEN 10
     WHEN escalated_tickets <= 1 THEN 5
     WHEN escalated_tickets <= 2 THEN 2
     WHEN escalated_tickets <= 3 THEN 1
     ELSE 0 END AS s_escalations,
...
-- Hard cap: an overdue payment or 2+ escalations caps the score at 6.
(payment_overdue = 'Y' OR escalated_tickets >= 2) AS capped
...
ROUND(CASE WHEN capped AND raw_score > 6 THEN 6 ELSE raw_score END + 1e-9, 1) AS health_score

The tiny 1e-9 is there for one account. Its raw score is exactly 3.25, which Excel rounds to 3.3. Floating-point maths can land on 3.2499999…, which would round to 3.2 and quietly break the match. Small details like this are why I check the results against the original, account by account.

Proving it matches the Excel model

Moving a score to a new system is only safe if the numbers don't move with it. The script has a --self-check mode that scores the sample data and compares it with the Excel model's published results:

The first pass found one difference: an expansion flag that came from Windows line endings in the CSV, not the logic. That's exactly the kind of bug a migration introduces and a spot check misses.

What changes each week

An account appears in the "changed" list when any of these is true since the last run:

  • It moved into red or amber.
  • Its score dropped by 1 point or more, whatever its band.
  • It became capped, because of a newly overdue payment or a second escalation.

The second rule matters most. A drop from 8.4 to 7.2 stays light green, so a band-only view shows nothing, but it's often the earliest warning there is.

The webhook URL is read from an environment variable, never stored in the code, so the script can be shared without sharing access to the channel.

What I'd connect next

  • Read from the CRM directly. Replace the CSV export with a call to the CRM's API (for example a Salesforce report or SOQL query), so nobody has to export anything.
  • Run it on a schedule. A weekly job (cron, or a scheduled GitHub Action) every Monday at 8am.
  • Write the score back. Push score, band and play to a field on the CRM or CS platform account record, so CSMs see it where they already work and can report on it.
  • Calibrate with history. Once score_history has a few quarters in it, compare past scores with who actually renewed and churned, and tune the weights.
