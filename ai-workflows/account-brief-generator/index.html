A pre-call brief that can't make up numbers

Before a customer call, a CSM needs two minutes of context, not twenty minutes in the CS platform. I built a workflow that has Claude write the brief from the health score data, then checks it so that a confident-sounding wrong number never reaches the call.

Skill shown
Using AI to speed up Customer Success work, with guardrails
The problem
Call prep means pulling together scores, red flags, metrics and the last play by hand. A language model can write that summary in seconds, but in a regulated customer base a brief with one invented figure is worse than no brief.
What I did
Built a script that sends one account's health score data to Claude, gets the brief back in a fixed structure, and checks it in code: every number must be in the data and every risk must cite the fields behind it. Data gaps are worked out by the code, not the model. If the check fails, nothing is saved.
Result
A brief for any of the eight accounts from the AI agent health score in one command, in the same five sections every time, with each risk traceable to its data.
Tools used
Claude API (structured outputs, refusal fallback), Python (written with Claude), CSV data from the AI agent health score

The accounts and figures are fictional, from the AI agent health score case study. The example brief below was written by hand, from Fenwick's data, to show the output format. A real run words it differently.

Why not just paste the account into a chatbot?

Because the risky part of an AI summary isn't the writing, it's the facts. A model asked to "summarise this account" may round a figure, merge two metrics, or fill a gap with something plausible. For an AI agent product sold to dental practices and gas engineers, the CSM is often the person explaining a safety incident. They need to know that every number in front of them is real.

So the workflow splits the job. The model does what it's good at: deciding what matters and writing it clearly. Code does what has to be exact: choosing the facts, listing what's missing, and checking the result.

How it works

  1. Gather the facts. The script joins the account's 24 metrics and red flags with its score, band, alert and weakest dimension, and adds the recommended play for that dimension. Blank metrics go on a data-gaps list.
  2. Ask Claude for a structured brief. The facts go to the Claude API with a short system prompt and a JSON schema, so the answer always comes back as a headline, situation, risks with evidence, three questions and a next step.
  3. Check it. Every number in the brief must appear in the facts (a rate of 0.8 may be written as 80%). Every risk must name the fields that support it, and each name must be a real field.
  4. Save or stop. A brief that passes is saved as a Markdown file with the data gaps added at the end. A brief that fails is not saved, and the script lists the problems.

The rules I gave the model

Use only the facts given. Every number you write must appear in the facts.
For each risk, put the exact names of the facts that support it in `evidence`.
If a red flag is set, lead with it.
Don't give clinical, legal or regulatory advice. Where one of those questions
comes up, say who should answer it.
Plain UK English, short sentences, no filler.

The prompt asks for good behaviour, but the check enforces it. I don't rely on a prompt alone for anything a customer could be harmed by.

The check, in code

for n in sorted(numbers_in(prose)):
    if not any(abs(n - a) < 1e-6 for a in allowed):
        problems.append(f"The number {n:g} isn't in the account data.")
for risk in brief["risks"]:
    for name in risk["evidence"]:
        if name not in facts:
            problems.append(f"Evidence {name!r} isn't a field in the account data.")

Its limit, stated plainly: it proves each number exists in the data, not that it's attached to the right metric. The evidence field is there so the CSM can check that in seconds.

Example: Fenwick Gas Services

Pre-call brief: Fenwick Gas Services

Heating and plumbing · Mid-market · Adoption · £60,000 ARR · renews 2027-05-01
Health score 49 (At risk). Alert: Red flag (critical safety incident; would be 73).

A critical safety incident in the last 30 days has capped Fenwick at 49. Without it the score would be 73.

Fenwick is a mid-market heating and plumbing customer in the Adoption stage, worth £60,000 a year and renewing on 2027-05-01. The score fell 21 points from 70. Outside AI quality the account looks solid: an 80% AI resolution rate, 80% coverage of eligible work, champion strength of 4 out of 5 and an NPS of 30.

Risks

  • Critical errors are running at 4.5 per 1,000 tasks, and one of them was a safety or compliance incident. A repeat would be hard to recover from. Evidence: Flag: critical safety or compliance incident (30 days); Q1 Critical errors per 1,000 tasks
  • 90% of escalations are picked up within SLA, so some urgent hand-offs still wait too long. For a gas engineer, that is where an emergency gets missed. Evidence: Q3 Escalations picked up within SLA
  • Staff may stop trusting the agent after the incident. The override rate is 10% today: watch it weekly. Evidence: Q2 Human override / edit rate

Questions to ask

  1. What happened on the call that caused the incident, and has your team changed how they use the agent since?
  2. Who on your side needs to see the fix before they're comfortable again?
  3. When the agent flags an emergency today, how quickly does a person pick it up?

Next step

Run a quality escalation: review the error with Product, fix the top three error patterns, confirm the hand-off time, then walk the champion through the fix.

Data gaps

None. Every metric has data.

All 22 numbers in this brief trace back to Fenwick's data, so it passes the check. Run it on Brightwater Clinics instead and the data-gaps section lists the metrics with no data yet, such as the outcome KPI and bypass rate, so the CSM asks about them rather than guesses.

Design choices

  • Structured output, not free text. A fixed schema means every brief has the same sections in the same order, so CSMs know where to look, and the check can read each part.
  • Code owns the gaps. Whether a metric is missing is a fact, not a judgement, so the model never decides it.
  • Fail closed. No brief is better than a wrong one. A failure prints exactly what was wrong so the prompt or data can be fixed.
  • A dry run first. --dry-run shows exactly what would be sent to the API, so anyone can review the data leaving the system before it does.
  • Refusals handled. If a safety classifier declines a request, the API retries on a fallback model, and the script stops cleanly if that also declines.

What I'd do next in a real team

  • Pull the facts from the CRM and the product's event data through their APIs instead of CSV exports.
  • Generate briefs automatically for every call booked in the next day, and post them to the CSM's channel.
  • Keep a small set of accounts with hand-checked briefs, and rerun them whenever the prompt or model changes, so quality is measured rather than assumed.
